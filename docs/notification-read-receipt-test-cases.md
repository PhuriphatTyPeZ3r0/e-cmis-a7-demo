# Test Cases: ระบบการแจ้งเตือนและ Read Receipt

## 1. วัตถุประสงค์

ตรวจสอบการแจ้งเตือนจาก workflow กิจกรรมที่ 7 ครบ 4 เหตุการณ์ การแยกผู้รับรายบุคคล การป้องกันข้อมูลซ้ำ การคำนวณวันทำการ และการเก็บหลักฐานการเปิดอ่านใน prototype ที่ใช้ `localStorage`

## 2. บัญชีทดสอบ

หน้า Login รับรหัสผ่านค่าใดก็ได้ หรือใช้ปุ่ม Quick Login

| บทบาท | Username | รหัสในระบบ |
|---|---|---|
| นักสืบสวน/เจ้าของสำนวน | `Somchai.I` | `investigator_demo` |
| ผอ.กองหรือ ผอ.สำนักงานเขต | `Narin.D` | `director_demo` |
| เจ้าหน้าที่ธุรการคดี | `Kanda.C` | `case_clerk_demo` |
| กลุ่มงานบริหารติดตามคดี กิจกรรมที่ 8 | `Suda.T` | `discipline_tracker_demo` |
| เจ้าหน้าที่กลุ่มงานกิจการคณะกรรมการ | `Siriporn.K` | `affairs` |
| เจ้าหน้าที่กลุ่มงานคำวินิจฉัยและมติ | `Thanakrit.B` | `board_sec` |

## 3. การเตรียมข้อมูล

1. เปิดระบบด้วย browser เดียวกันตลอดชุดทดสอบ เพราะข้อมูล notification ของ prototype อยู่ใน browser นั้น
2. เลือกสำนวนที่อยู่ในสถานะพร้อมบรรจุวาระสำหรับชุด A
3. เลือกสำนวนที่บันทึกมติแล้ว (`RESOLVED`) สำหรับชุด C
4. เลือกสำนวนชี้มูลที่เปิดหน้า `ruling-report.html` และมีแท็บหนังสือลงโทษทางวินัยสำหรับชุด D
5. ก่อนเริ่มรอบใหม่ สามารถล้างเฉพาะ local cache ผ่าน DevTools Console แล้ว reload หน้า:

```javascript
localStorage.removeItem('ecmis.notifications.v1');
localStorage.removeItem('ecmis.notificationReceipts.v1');
location.reload();
```

เมื่อติดตั้ง database migration แล้ว การ reload จะโหลดรายการจาก Supabase กลับมาอีกครั้ง การล้าง localStorage จึงไม่ใช่การลบข้อมูลในฐานข้อมูล ห้ามล้าง localStorage ระหว่าง TC ที่ต้องตรวจการคงอยู่ของข้อมูลหลัง reload หรือการสลับบัญชี

สำหรับการทดสอบฐานข้อมูลครั้งแรก ให้รัน `sql/create_notification_store.sql` แล้วตามด้วย `sql/seed_notification_demo.sql` ใน Supabase SQL Editor จากนั้นหน้า Notification Center ต้องแสดง badge `ข้อมูลจากฐานข้อมูล`

## 4. Test Cases

### A. Demo Accounts และสิทธิ์ใช้งาน

#### TC-NOT-001 — Quick Login ของบัญชีผู้รับทั้ง 4 ประเภท

**ขั้นตอน**

1. เปิด `login.html` หรือ `/res/login.html`.
2. คลิก Quick Login ของ `Somchai.I`.
3. ตรวจ URL และชื่อผู้ใช้ใน sidebar.
4. Logout แล้วทำซ้ำกับ `Narin.D`, `Kanda.C` และ `Suda.T`.

**ผลที่คาดหวัง**

- ทุกบัญชี Login สำเร็จและเปิด `notifications.html` เป็นหน้าหลัก
- Sidebar แสดงชื่อและบทบาทตรงกับบัญชีที่เลือก
- ไม่มี notification ของบัญชีอื่นปะปน

#### TC-NOT-002 — RBAC ของบัญชีผู้รับการแจ้งเตือน

**ขั้นตอน**

1. Login ด้วยบัญชีผู้รับบัญชีใดบัญชีหนึ่ง
2. พิมพ์ URL ของหน้าปฏิบัติงาน เช่น `agenda-set.html` หรือ `board-resolution.html` โดยตรง

**ผลที่คาดหวัง**

- ระบบไม่เปิดหน้าที่ไม่มีสิทธิ์
- ระบบนำกลับหน้า Notification Center และแจ้งว่าไม่มีสิทธิ์

### B. การบรรจุวาระและ Reminder

#### TC-NOT-003 — แจ้งทันทีเมื่อบรรจุวาระสำเร็จ

**ขั้นตอน**

1. Login เป็น `affairs`
2. เปิดสำนวนที่พร้อมบรรจุวาระใน `agenda-set.html`
3. กรอกครั้งประชุม วันที่ประชุม และเลขวาระให้ครบ
4. ทำ checklist และยืนยันบรรจุวาระ
5. Login สลับกันเป็น `Somchai.I`, `Narin.D` และ `Kanda.C`
6. เปิด Notification Center ของแต่ละบัญชี

**ผลที่คาดหวัง**

- ผู้รับทั้ง 3 บัญชีได้รับ `บรรจุวาระการประชุมแล้ว` บัญชีละ 1 รายการ
- รายการแสดงประเภท `บรรจุวาระ`, เลขสำนวน, ผู้ส่ง และเวลาส่ง
- `Suda.T` ไม่ได้รับรายการนี้
- รายการเริ่มต้นเป็น `ยังไม่ได้อ่าน`

#### TC-NOT-004 — ยกเลิกหรือบันทึกล้มเหลวต้องไม่แจ้งเตือน

**ขั้นตอน**

1. เปิดหน้าบรรจุวาระด้วยสำนวนที่ยังไม่เคยส่ง
2. คลิกบรรจุวาระ แล้วเลือกยกเลิกในกล่องยืนยัน
3. ทำอีกครั้งโดยปล่อยข้อมูลบังคับไม่ครบเพื่อให้ validation ไม่ผ่าน
4. ตรวจ Notification Center ของผู้รับทั้ง 3 บัญชี

**ผลที่คาดหวัง**

- ไม่เกิด notification ใหม่จากทั้งสองกรณี
- Badge ไม่เพิ่ม

#### TC-NOT-005 — ป้องกัน notification บรรจุวาระซ้ำ

**ขั้นตอน**

1. ทำ TC-NOT-003 สำเร็จ 1 ครั้ง
2. Reload หน้าบรรจุวาระและ Notification Center หลายครั้ง
3. หากปุ่ม workflow ยังเปิดให้กด ให้ลองส่งข้อมูลเดิมซ้ำ

**ผลที่คาดหวัง**

- แต่ละบัญชียังคงมี event เดิมเพียง 1 รายการ
- Reload หรือส่งซ้ำไม่เพิ่ม Badge และไม่สร้างรายการซ้ำ

#### TC-NOT-006 — Reminder ก่อนประชุมวันจันทร์

**ข้อมูลทดสอบ:** วันประชุม `07/09/2569` หรือ `2026-09-07`

**ขั้นตอน**

1. สร้าง event บรรจุวาระที่มีวันประชุมตามข้อมูลทดสอบ
2. จำลองวันที่เปิดระบบเป็น `04/09/2026` หรือเรียกใน DevTools:

```javascript
ECMIS.NotificationStore.ensureDueAgendaReminders('2026-09-04');
```

3. เปิด Notification Center ของผู้รับทั้ง 3 บัญชี

**ผลที่คาดหวัง**

- ได้ `เตือนประชุมล่วงหน้า 1 วันทำการ` ในวันศุกร์ที่ 4 กันยายน 2569
- ผู้รับตรงกับ notification บรรจุวาระเดิมทั้ง 3 บัญชี
- แต่ละบัญชีได้รับเพียง 1 รายการ

#### TC-NOT-007 — Reminder ข้ามวันหยุดราชการและรองรับ พ.ศ./ค.ศ.

**ข้อมูลทดสอบ:** วันประชุม `13/08/2569` ซึ่งวันก่อนหน้า `12/08/2569` เป็นวันหยุด

**ขั้นตอน**

1. เปิดหน้าใดก็ได้หลัง Login
2. ตรวจผ่าน DevTools:

```javascript
ECMIS.previousThaiBusinessDay('2569-08-13');
ECMIS.previousThaiBusinessDay('2026-08-13');
```

**ผลที่คาดหวัง**

- ทั้งสองคำสั่งคืนค่า `2026-08-11`
- วันที่ พ.ศ. และ ค.ศ. ให้ผลวันทำการเดียวกัน

#### TC-NOT-008 — ไม่สร้าง Reminder ย้อนหลังหลังวันประชุม

**ขั้นตอน**

1. สร้าง event ที่มีวันประชุม `07/09/2569`
2. เรียก scheduler ด้วยวันที่หลังประชุม:

```javascript
ECMIS.NotificationStore.ensureDueAgendaReminders('2026-09-08');
```

3. ตรวจ Notification Center ของผู้รับ

**ผลที่คาดหวัง**

- ไม่เกิด `AGENDA_REMINDER` ใหม่ย้อนหลัง

### C. การบันทึกและส่งมติ

#### TC-NOT-009 — บันทึกมติอย่างเดียวยังไม่แจ้งเตือน

**ขั้นตอน**

1. Login ด้วยบทบาทที่บันทึกมติได้
2. เปิด `board-resolution.html` หรือ `resolution.html`
3. บันทึกมติจนสำเร็จ แต่ยังไม่กด `ส่งมติและเอกสารคืนผู้รับผิดชอบ`
4. ตรวจ Notification Center ของ `Somchai.I`, `Narin.D` และ `Kanda.C`

**ผลที่คาดหวัง**

- ไม่พบ notification ประเภท `ส่งมติ`
- การบันทึกมติไม่ถูกตีความว่าเป็นการส่งมติ

#### TC-NOT-010 — แจ้งทันทีหลังส่งมติสำเร็จ

**ขั้นตอน**

1. เปิดสำนวนที่บันทึกมติแล้ว
2. คลิก `ส่งมติและเอกสารคืนผู้รับผิดชอบ`
3. ยืนยันการส่ง
4. ตรวจ Notification Center ของผู้รับทั้ง 3 บัญชี

**ผลที่คาดหวัง**

- ผู้รับทั้ง 3 ได้ notification ประเภท `ส่งมติ` บัญชีละ 1 รายการ
- เวลาส่งถูกบันทึกทันที
- สำนวนมีค่า `resolutionDispatchedAt`
- ปุ่มเปลี่ยนเป็นสถานะ `ส่งมติและเอกสารแล้ว`

#### TC-NOT-011 — ป้องกันการส่งมติซ้ำ

**ขั้นตอน**

1. ทำ TC-NOT-010 สำเร็จ
2. Reload หน้า และลองกดปุ่มเดิมอีกครั้ง
3. ตรวจ Notification Center ของผู้รับ

**ผลที่คาดหวัง**

- ปุ่มถูก disable หรือไม่ดำเนินการซ้ำ
- Notification `ส่งมติ` ยังคงมีเพียง 1 event ต่อสำนวน/การส่งนั้น

### D. หนังสือลงโทษทางวินัย กิจกรรมที่ 8

#### TC-NOT-012 — ปุ่มส่งกิจกรรมที่ 8 แสดงเฉพาะแท็บวินัย

**ขั้นตอน**

1. Login ด้วยผู้ใช้ที่แก้ไข `ruling-report.html` ได้
2. เปิดแท็บเอกสารอื่น เช่น รายงานวินิจฉัย
3. ตรวจ action bar
4. เปิดแท็บ `หนังสือลงโทษทางวินัย` และ `แจ้งโทษวินัย (v.2)`

**ผลที่คาดหวัง**

- แท็บที่ไม่ใช่วินัยไม่แสดงปุ่ม `ส่งหนังสือไปกิจกรรมที่ 8`
- แท็บวินัยทั้งสองแบบแสดงปุ่มดังกล่าว

#### TC-NOT-013 — ส่งหนังสือวินัยให้กลุ่มกิจกรรมที่ 8 เท่านั้น

**ขั้นตอน**

1. จากแท็บวินัย คลิก `ส่งหนังสือไปกิจกรรมที่ 8` และยืนยัน
2. Login เป็น `Suda.T` และตรวจ Notification Center
3. ตรวจบัญชี `Somchai.I`, `Narin.D` และ `Kanda.C`

**ผลที่คาดหวัง**

- `Suda.T` ได้ notification `ได้รับหนังสือลงโทษทางวินัย` 1 รายการ
- บัญชีผู้รับอีก 3 ประเภทไม่ได้รับ event นี้
- สำนวนมีค่า `disciplineActivity8SentAt`
- ปุ่มเปลี่ยนเป็น `ส่งไปกิจกรรมที่ 8 แล้ว`

#### TC-NOT-014 — ป้องกันการส่งกิจกรรมที่ 8 ซ้ำ

**ขั้นตอน**

1. ทำ TC-NOT-013 สำเร็จ
2. Reload หน้า แล้วกลับไปยังแท็บวินัย
3. ลองกดปุ่มส่งอีกครั้งและตรวจรายการของ `Suda.T`

**ผลที่คาดหวัง**

- ปุ่มถูก disable
- ไม่มี notification ซ้ำ และ Badge ไม่เพิ่มซ้ำ

### E. Badge และ Read Receipt

#### TC-NOT-015 — Badge แยกตามบัญชี

**ขั้นตอน**

1. ทำ TC-NOT-003 เพื่อสร้าง event ให้ผู้รับ 3 บัญชี
2. Login เป็น `Somchai.I` แล้วอ่านรายการนั้น
3. สลับเป็น `Narin.D` และ `Kanda.C`

**ผลที่คาดหวัง**

- Badge ของ `Somchai.I` ลดลง 1
- Badge ของ `Narin.D` และ `Kanda.C` ยังไม่ลด
- Read Receipt ของแต่ละบัญชีไม่ปะปนกัน

#### TC-NOT-016 — เปิด dropdown หรือ Notification Center ไม่เคลียร์ Badge

**ขั้นตอน**

1. Login ด้วยบัญชีที่มี unread อย่างน้อย 2 รายการ
2. จดจำนวน Badge
3. เปิด dropdown รูปกระดิ่งแล้วปิด โดยไม่คลิกรายการ
4. เปิด `notifications.html` โดยยังไม่คลิกรายการ
5. Reload หน้า

**ผลที่คาดหวัง**

- Badge คงค่าเดิมทุกขั้นตอน
- รายการทั้งหมดยังคงเป็น `ยังไม่ได้อ่าน`

#### TC-NOT-017 — อ่านทีละรายการและบันทึก Timestamp

**ขั้นตอน**

1. Login ด้วยบัญชีที่มี unread อย่างน้อย 2 รายการ
2. คลิก notification เพียง 1 รายการ
3. ตรวจ Badge, สถานะรายการ และแผงหลักฐาน

**ผลที่คาดหวัง**

- Badge ลดลง exactly 1
- เฉพาะรายการที่คลิกเปลี่ยนเป็น `อ่านแล้ว`
- แสดงวันและเวลาอ่านของบัญชีปัจจุบัน
- ผู้รับคนอื่นยังแสดง `ยังไม่ได้อ่าน`

#### TC-NOT-018 — readAt บันทึกครั้งแรกเพียงครั้งเดียว

**ขั้นตอน**

1. จด Timestamp จากรายการที่อ่านแล้วใน TC-NOT-017
2. รออย่างน้อย 1 นาที แล้วคลิกรายการเดิมอีกครั้ง
3. Reload หน้าและตรวจ Timestamp

**ผลที่คาดหวัง**

- Timestamp ไม่เปลี่ยนจากค่าครั้งแรก
- สถานะ `อ่านแล้ว` และ Timestamp ยังคงอยู่หลัง reload

#### TC-NOT-019 — ข้อมูลที่ต้องแสดงใน Notification Center

**ขั้นตอน**

1. เปิด Notification Center ที่มีทั้ง unread และ read
2. สลับ filter `ยังไม่ได้อ่าน` และ `ทั้งหมด`
3. คลิกรายการเพื่อเปิดหลักฐานของสำนวน

**ผลที่คาดหวัง**

- Filter unread แสดงเฉพาะรายการยังไม่อ่าน
- Filter ทั้งหมดแสดงทั้งสองสถานะ
- แต่ละรายการมีประเภท เลขสำนวน ผู้ส่ง เวลาส่ง และเวลาอ่านเมื่ออ่านแล้ว
- หลักฐานของสำนวนแสดงผู้รับทุกคน พร้อมสถานะและ Timestamp รายบุคคล

### F. Route และ Responsive

#### TC-NOT-020 — Root/`res` และ responsive layout

**ขั้นตอน**

1. ทำ TC-NOT-001, TC-NOT-016 และ TC-NOT-019 ที่ `notifications.html`
2. ทำซ้ำที่ `/res/notifications.html`
3. ทดสอบ viewport desktop, tablet และ mobile

**ผลที่คาดหวัง**

- Root และ `/res/` ให้ผลเหมือนกัน
- Dropdown, Badge, filter, รายการ และแผงหลักฐานใช้งานได้
- ไม่มีข้อความหรือปุ่มล้น viewport และสามารถ scroll เพื่อดูข้อมูลครบ

## 5. Acceptance Criteria สรุป

ถือว่าผ่าน defect เมื่อ TC-NOT-001 ถึง TC-NOT-020 ผ่านทั้งหมด โดยเฉพาะเงื่อนไขสำคัญต่อไปนี้:

- การบรรจุวาระและการส่งมติแจ้งผู้รับ 3 บัญชีที่กำหนดเท่านั้น
- หนังสือวินัยแจ้งบัญชีกิจกรรมที่ 8 เท่านั้น
- บันทึกมติอย่างเดียวไม่สร้าง notification
- Badge ไม่หายจากการเปิด dropdown หรือหน้า Notification Center
- การอ่านรายการหนึ่งรายการลด Badge หนึ่งหน่วย และเก็บ `readAt` ครั้งแรกถาวรใน browser
- Reload หรือ action ซ้ำไม่สร้าง event ซ้ำ
- Reminder ใช้วันทำการก่อนประชุมและไม่สร้างย้อนหลังหลังวันประชุม
